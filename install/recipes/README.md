# Install recipes

One YAML per app, mirroring `control/registry/apps/` ids. Phase 0 files are skeletons
generated by `tools/gen-registry-stubs.py`; `PIN-ME` markers mark fields the kit
builder must pin (URL + SHA-256) at Phase 4.

Strategies (spec §8): `dnf`, `dnf-verify` (audit decides dnf vs build), `build`,
`tarball`, `wine` (user-supplied installer), `pip-vendored`, `static`.

Rules:
- VARA-family recipes reference `kit-import/` artifacts and **never** embed download URLs (G6).
- Every pinned artifact records `sha256`; the builder writes them into the kit manifest.
- Every recipe records `license:` — the upstream SPDX id used for attribution and the kit
  manifest (spec §13). `TBD-VERIFY-AT-PIN` marks licenses that must be confirmed when the
  `PIN-ME` fields are resolved (Doctor flags them at kit build). `wine` recipes carry
  `wine.license: user-supplied` instead (G6). Inventory: `docs/audit/third-party-licenses.md`.
- Recipe strategy must match the registry entry's `install.strategy` (enforced by tests).

## Config blocks (P4 M7, spec §6.2)

Native apps' adapters write ONLY the keys their recipe declares, under a
top-level `config:` block — the VARA `wine.ini_set:` precedent generalized:

```yaml
recipe:
  config:
    set:                                  # structured formats (JSON/YAML): dotted keys
      - {key: mycall, value: "{callsign}"}
    # INI-family apps (qttermtcp, xygrib, paracon, artemis) use {section, key, value}
    # osm-navit uses {xpath, attribute, value} rows (relative xpaths, seeded overlay)
    # ardop manages config.args instead (a list of launch arguments — ardopcf has
    # no config file; the managed service consumes <state>/app-args/ardop.args)
```

- `value` may template `{callsign}` and `{grid}` from the station profile;
  unknown tokens and empty profile fields refuse with the exact fix.
- `[]` rows are deliberate: the mechanism + path are pinned from each app's
  own source/artifact at M7; exact key names are pinned at the live E2E
  (same discipline as VARA's `wine.ini_set`).
- `config.file:` (artemis) overrides which file in the prefs dir the
  adapter manages. Adapter paths live in `control/core/adapters/*.py`
  docstrings (with the upstream evidence) and in each registry entry's
  `native_path`.
- Adapter reads mask any credential-shaped key (reg/password/passwd/key/
  token/secret/passcode, case-insensitive) as `***` — presence is surfaced,
  never contents (G6).
- Every write is preceded by a timestamped backup under
  `<state>/config-backups/<app>/` and lands atomically (tmpfile +
  `os.replace`); re-applying an in-sync config writes nothing.

## Postinst steps (M11a, spec §5)

A recipe's `postinst:` list names declarative setup steps the bootstrap
executor (`gd_kit_postinst`, `install/lib/kit.sh`) applies per selected app
after payload placement — in canonical order dialout → udev → units →
wine-prefix → wine-install:

```yaml
recipe:
  postinst:
    - units             # render + install the grid-down-* user unit set (operator's dirs)
    - dialout           # operator -> dialout group (serial-port access)
    - udev: udev/99-grid-down-<app>.rules   # file must exist under install/udev/
    - wine-prefix       # wine-strategy only: unpack the kit's cached prefix tarball
    - wine-install      # wine-strategy only: silent kit-import installer run (G6)
```

Rules (resolver-enforced, `install/bundle-builder/resolve-kit.py`):
- Known steps only; bare steps are exact literals. No command strings, no
  metacharacters — the air-gap side never interprets shell from a recipe
  (steps travel as `kit/postinst.tsv` columns, not code).
- `wine-*` steps are only valid on `strategy: wine` recipes. The installer
  file, mode and flags keep living in the recipe's `wine:` block — the single
  source the suite reads (`gd winehub install <id>`); the executor delegates.
- `udev:` targets must match `udev/<name>.rules` and the file must exist in
  `install/udev/` (the kit carries it; see `install/udev/README.md`).
- Steps needing an operator identity (`--user` flag, or sudo's `SUDO_UID`)
  skip with a loud note naming the follow-up command; real failures stop the
  install naming the step. Every step self-guards, so re-running bootstrap
  after a fix resumes where it stopped.

M11a flips: direwolf/fldigi/hamlib declare `units` + `dialout`; the VARA
family declares `dialout` + `wine-prefix` + `wine-install` (kit-import
artifacts + the prefix tarball are packed from M11b). meshtasticd stays `[]`
— the daemon is explicit-start by design (P4 M9).
